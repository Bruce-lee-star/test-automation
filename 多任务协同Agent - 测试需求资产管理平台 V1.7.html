V1.7 更新说明（基于 V1.6 评审）：
  1. 需求判定证据链：每次判定必须输出 confidence(0-1) + judgmentEvidence(对比了哪些字段/标签/关键词)，confidence < 0.7 走人工门禁；Modify/BugFix/Deprecated 强制人工确认才进入 Vn+1。
  2. 测试点稳定 ID：每个测试点分配 TP-xxx，版本升级 ID 不变，内容变更；基线比对改为 ID 集合 diff + 同 ID 文本 diff，不再纯文本比对。
  3. 资产状态机：Draft → InReview → Approved → Archived → Deprecated，杜绝"旧版本不可改但不知谁审过"。
  4. 幂等性：同 (assetId, storyNumber, reqType) 已有 Draft 版本则复用，不新建 Vn+1。
  5. RoleElementPicker 定位评分系统：每个候选定位器打 0-100 分，按 role+name > data-testid > aria-label > 稳定 class/id > 锚点 xpath > 绝对 xpath > 视觉OCR 排序；低于阈值标记 unstable。
  6. 元素覆盖率报告：探测完成输出 accessible / degraded / unsupported 三栏统计，Canvas/Shadow DOM/富文本显式标记。
  7. 降级定位链：首选失败自动按分数降序尝试下一档，TestFlow 记录最终采用的定位策略。
  8. 输入门禁：Story 字数 / Acceptance Criteria 缺失直接拒，标 NeedsClarification，不硬编。
  9. Prompt 版本化：判定/挖掘 prompt 存入资产库并打版本号，可回溯。
  10. 资产入库走 Git：本地产出 → git commit（人工触发），不上四层权限/审计平台。

门禁规则
  • confidence < 0.7 → 强制人工确认，不自动选类型
  • Modify / BugFix / Deprecated → 无论置信度多少都人工确认（高风险）
  • 兜底策略：置信度不足时默认 Modify（影响面最大、最保守）
  • 审批人：测试负责人 + 产品负责人双签

RoleElementPicker 定位评分系统（v1.7 新增）

每个交互元素采集时，Picker 同时产出 top-N 候选定位器，按下表打分，选最高分入 TestFlow；失败自动降级到下一档。

档位 定位策略 基准分 稳定性说明
Srole + accessible-name + exact95首选，语义定位
Adata-testid / data-test / data-qa90开发配合，最稳
Brole + accessible-name (substring)75次选，容忍文案微调
Caria-label70图标按钮常见
D稳定 id / 非 hash class55React/Vue scoped class 会扣到 30
E相对 xpath + 邻近锚点40必须带锚点，否则扣到 20
F绝对 xpath / CSS nth-child15默认禁用，仅兜底
G视觉/OCR 定位10Canvas/图表专用

扣分规则（叠加在基准分上）

  • 同一页面出现 多个同 role+name：-30（命中唯一性失败）
  • class/id 含 hash（sc-1a2b3c、ember123）：-40
  • 定位器跨 iframe / Shadow Root：-20
  • 动态文本（含日期/数字）在 name 里：-15
  • 元素在探测中出现率 < 100%（多轮快照里时有时无）：-25

输出示例（每个元素一条）

{
  "element": "提交按钮",
  "best": { "strategy": "role+name-exact", "score": 92, "selector": "button[role=button][name=提交]" },
  "candidates": [
    { "strategy": "aria-label", "score": 68, "selector": "button[aria-label=提交]" },
    { "strategy": "xpath-anchor", "score": 38, "selector": "//form[@id=login]//button[.='提交']" }
  ],
  "finalScore": 92,
  "stability": "stable | degraded | unstable",
  "fallbackChain": ["role+name-exact", "aria-label", "xpath-anchor"]
}
阈值： finalScore ≥ 70 → stable；40-69 → degraded（TestFlow 里自动串降级链）；< 40 → unstable（报告里标红，要求人工介入或开发补 testid）。

🔑 元素是一等公民：ElementRepository（跨 case 复用）

元素定位器不绑定在单个 case 里，而是独立成元素库，全局唯一 ID。多个 case 引用同一元素时，定位器只维护一份——登录页"提交按钮"被 50 个 case 用，改一次全量生效。

{
  "elementId": "ELEM-LOGIN-SUBMIT-001",
  "page": "/login",
  "semanticName": "提交按钮",
  "best": { "strategy": "role+name-exact", "selector": "button[name=提交]", "score": 92 },
  "fallbackChain": ["aria-label", "xpath-anchor"],
  "lastVerifiedAt": "2026-10-13T10:00:00",
  "verifyPassRate": 1.0,
  "usedByCases": ["LOGIN-001", "LOGIN-002", "LOGIN-010"]
}

✅ 回放验证门禁（生成 ≠ 可用）

定位器生成后不许直接入库，必须过回放验证：

  • 关闭缓存重跑：清掉 storageState / cookies，重新登录后再找一次元素
  • 换数据重跑：用另一套测试账号 / 另一环境（SIT2 vs SIT3）再找一次
  • 多次重跑：同一元素连续找 N 次（默认 N=3），每次都能唯一命中才算 stable
  • 出现率记录：命中次数/N，写入 verifyPassRate；< 0.9 自动降级为 unstable

🔗 影响面分析（元素变了哪些 case 会挂）

每次版本 diff 时，对 ElementRepository 做 diff：

元素变更类型影响动作
定位器 selector 改了usedByCases 里所有 case报告列出受影响 case，强制回归
元素被删除引用它的 case 全部断链阻断入库，先处理引用
score 从 90 掉到 60降级为 degradedTestFlow 自动切 fallbackChain
新元素加入无正常入库

🛡️ 多轮快照一致性校验

动态交互探测时同一元素会在多轮快照里出现。若 role/name 在不同轮次里不一致（比如 name 从"提交"变成"提交(1)"），说明元素是动态生成的，定位器必须用更稳的策略（testid / aria-label），不能信 role+name。这一步在 Picker 内部自动做，结果写进 candidates[].score 扣分。

四、MCP 探测链路（产出 PageModel）

  1. 读凭证池（环境变量注入，日志脱敏），登录目标系统
  2. DOM 属性抓取：每个表单元素读 type / required / min / max / minlength / maxlength / pattern / options / data-*——这是字段类型和约束的主来源
  3. 无障碍树补充：补 label / role / accessible-name（图标按钮、无 label 场景）
  4. 动态交互循环：切下拉/输入/点 Tab，每轮 diff DOM，记录"父字段变了谁重载"→ 建 dependsOn / cascade
  5. 网络监听：拦截提交请求，记录每个 action 触发的 API（用于 API 级断言）
  6. 每个字段/动作送 RoleElementPicker，产出 top-N 定位候选 + 评分 + 回放验证
  7. 按 PageModel 自动生成 TP + 用例设计方法映射
  8. 生成 Feature + Step，过输出门禁（Cucumber 可解析 + Step 绑定）
  9. 写资产新版本，git commit（人工 push）

覆盖率看板（多维，每次任务必出）

覆盖率分 5 层，从 Story 到自动化脚本全链路追溯。任何一层 < 阈值都在报告里标红，不允许"跑完就算完"。

层 口径 阈值 未达标动作
L1 Story 字段完整度 Jira Story 里 AC / 前置条件 / 负责人 / 验收标准 填齐的比例 ≥ 80% 未达标 → 输入门禁拒绝，返回补全清单
L2 需求→测试点覆盖率 Story 每条显性需求是否都拆出了 ≥1 个 TP 100% 有未覆盖需求 → 报告列清单，Agent 补挖
L3 测试点→手工用例覆盖率 每个 TP 是否都有手工 case（手工 case 是唯一源，自动化 case 从手工 case 派生） P0=100% / P1≥90% / P2≥50% 缺 P0 case → 阻断入库
L4 手工用例→自动化覆盖率 手工 case 里有对应 Cucumber 自动化的比例（自动化 case 由手工 case 派生，不独立存在） 核心链路 ≥ 60% / 全量 ≥ 30% 不阻断，但报告里给出下一轮补自动化建议
L5 定位器稳定率 生成的定位器里 score≥70(stable) 的比例 ≥ 80% < 80% → 列出 unstable 元素清单，要求开发补 testid 或人工写脚本
